# 작업별 개발 절차

상태: 2026-10-02 사용자와 확정한 작업 규칙을 문서화했다. 자동 하네스·CI·AI 리뷰·GitHub 병합 보호 설정의 완료 기록은 아니다. 공통·Django 제품 계획의 저장소 내 snapshot 연결은 후속 작업이다.

## 작업 시작

1. [루트 작업 규칙](../../AGENTS.md)과 이 문서를 읽는다. 요청이 확인·진단인지 구현인지 구분한다.
2. 작업별 라우팅에서 관련 명세·현재 구현·기존 증거를 확인한다. 관련 없는 모든 문서를 일괄 읽지는 않는다.
3. 현재 브랜치, 기준 브랜치와 작업 트리를 확인한다. 기존 변경은 사용자 소유로 보존한다. 겹치는 변경, 미병합 선행 작업, 미확정 정책은 질문한다.
4. 구현 요청이면 최신 기준에서 허용된 작업 브랜치를 먼저 만든다. 검토만 요청받았다면 구현 브랜치나 수정 작업을 시작하지 않는다.
5. 장기·구조 작업은 `docs/plans/`에 목표·범위·현재 사실·변경 파일·수용 기준·검증 명령·실패 대응·진행 상태를 먼저 적는다.

현재 제품 계획 원본은 작업공간의 `InnerNavi_V2_Common.md`와 `InnerNavi_V2_Django.md`이며, 이 저장소의 clone만으로는 제공되지 않는다. 요구사항이 필요한 작업은 원본 또는 검증된 snapshot을 확보한 뒤 진행한다. 없는 명세를 추측해서 구현하지 않는다. 기존 계획의 초기 브랜치 설명보다 아래의 최신 사용자 확정 규칙을 적용한다. 원본과 snapshot의 경로·연결 정리는 후속 작업이며 이 문서가 제품 명세를 대체하지 않는다.

## 작업별 라우팅

모든 작업은 루트 규칙과 이 문서가 공통 진입점이다. 아래는 추가로 확인할 범위이며, 이름만 있는 디렉터리를 구현된 명세·검사로 오인하지 않는다.

| 작업 | 먼저 확인할 내용 | 수정 경계 | 종료 전 검증 |
| --- | --- | --- | --- |
| Django 백엔드 | 관련 API·계정·권한·상태 명세, Django 계획의 계층 경계, 기존 backend 테스트 | HTTP/큐 어댑터와 서비스 계층, 모델·migration, 관련 계약·테스트 | Django check, migration 변경 검사, Ruff, 관련 pytest. DB 제약·트랜잭션은 실제 PostgreSQL로 검사 |
| Vue 웹 | 관련 API·역할별 화면·모바일 고려 기준, 현재 API 연결·웹 테스트 | 화면·상태·API 어댑터와 관련 테스트. UI 숨김을 서버 권한으로 간주하지 않음 | Vue 타입 검사 포함 build, Vitest. 기능별 직접 확인·E2E는 구현 상태에 따라 보고 |

| 문서 | 원본·연결 문서, 확정 결정과 실제 구현 상태 | 관련 문서·안내·템플릿. 미확정 정책을 확정처럼 추가하지 않음 | 링크·앵커·구조·코드 펜스·표현 일치·실제 상태 확인 |
| 하네스·CI·배포 | 검증·사람 승인·배포/복구 계약, ADR·runbook·현재 설정 | 해당 스크립트·workflow·infra·테스트·문서. 실제 외부 설정은 별도 승인 | 존재하는 스크립트·구성·관련 빌드/health 검사, 게이트 구현 시 고의 실패 차단 확인 |
| 개발 환경·버전 | [실행 환경 ADR](../adr/0001-development-runtime.md), [로컬 실행 문서](local-development.md), 잠금 파일 | 프로젝트 도구·의존성·이미지와 관련 문서. 전역 설치·PATH 자동 변경 금지 | 잠금 설치 확인과 영향받는 실행·타입·테스트·빌드·Compose 검사 |

여러 영역을 바꾸면 관련 행을 함께 적용한다. 요청 범위 밖 API/DB 계약·의존성·버전 변경은 영향과 이유를 설명하고 승인받는다. 단순 문서 수정에 관계없는 전체 앱 실행을 요구하지 않지만 실행 계약을 바꾼 문서는 영향을 받는 영역도 확인한다.

## 문서 책임

- `docs/specs/`: 저장소의 명세 디렉터리. 현재는 자리만 있고 공통 명세 snapshot은 없다. 기존 원본의 `docs/spec` 표기는 연결 작업에서 정리하며 중복 디렉터리를 임의 생성하지 않는다.
- `docs/architecture/`: 구성 요소 책임과 경계.
- `docs/adr/`: 확정한 기술 선택·대안·근거.
- `docs/plans/`: 실행 순서·범위·수용 조건·진행 상태.
- `docs/solutions/`: 실제로 검증한 해결. 추측 중인 대응은 해결 완료로 기록하지 않는다.
- `docs/runbooks/`: 개발·운영·배포·복구 절차.
- `docs/evidence/`: 실제 환경·명령·관측 결과. 과거 실행 증거를 현재 재실행 결과로 표현하지 않는다.

명세 → 작업 계획 → 코드·회귀 테스트 → 수동 PR → CI 결과 → 배포 이미지/기록의 연결을 단계별로 만든다. 현재 연결되지 않은 단계는 미완료다. 반복 지적은 먼저 명세·회귀 테스트에 반영하고, 재발 시 린터·스크립트·CI로 자동화한다.

## 브랜치 규칙

허용된 작업 브랜치는 다음과 같다. 한 브랜치는 한 작업 목적을 담고 작업명은 영어 소문자 단어를 하이픈으로 연결한다.

| 유형 | 용도 | 예시 |
| --- | --- | --- |
| `feature/*` | 기능 추가 | `feature/admin-approval` |
| `fix/*` | 오류 수정 | `fix/health-timeout` |
| `refactor/*` | 기존 동작을 유지하는 구조 개선 | `refactor/route-service` |
| `chore/*` | 도구·개발 기반·설정 작업 | `chore/verify-entrypoint` |
| `docs/*` | 문서 작업 | `docs/agent-rules` |
| `test/*` | 테스트 작업 | `test/graph-determinism` |

`codex/*`, `claude/*` 등 도구가 제안하는 다른 유형을 사용하지 않는다. `main`·`dev`만 기준·통합 브랜치 이름으로 예외를 둔다. 이 예외는 직접 작업·커밋·무검수 병합 허용이 아니다. `release/*` 등 추가 전략은 확정되지 않았으므로 임의 도입하지 않는다.

### 초기 기반 작업

- 최신 `main` → 허용된 작업 브랜치 → 사용자가 직접 만든 PR → 사용자 검수·`main` 병합.
- 기존 커밋이 병합되었어도 남은 기반 작업을 `main`에서 직접 구현하지 않는다.
- 공통 명세 연결·최소 하네스/CI 등 기반 작업은 아직 남아 있다. 이번 규칙 확정만으로 `dev`를 생성하지 않는다.

### 기반 작업 완료 이후

- 기반 작업 완료 시 최신 `main`에서 `dev`를 생성한다.
- 최신 `dev` → 허용된 작업 브랜치 → 수동 PR·검수 → `dev` 병합.
- 배포 대상 통합은 수동 `dev` → `main` PR과 사용자 검수를 거친다.

`dev`는 개발 결과의 통합 브랜치이며 개발 문서만 보관하는 브랜치가 아니다. 생성 시점 전에는 존재한다고 전제하지 않는다.

### 선행 작업과 안전한 분기

새 작업에 아직 병합되지 않은 다른 작업의 코드가 필요하면 진행 순서를 질문한다. 확정한 방식은 선행 작업을 먼저 검수·병합한 뒤 최신 기준에서 새 브랜치를 만드는 것이다. 미병합 브랜치 위에 새 브랜치를 쌓거나 기준 브랜치에 선행 코드를 직접 복사하지 않는다.

분기 전 Git Bash에서 `git status --short --branch`, `git branch -vv`, 기준/작업 브랜치 존재 여부를 확인한다. 깨끗한 작업 트리와 올바른 remote를 확인한 뒤 해당 기준만 fetch하고 `git merge --ff-only origin/main` 또는 `origin/dev`로 동기화한다. fast-forward가 불가능하면 강제로 맞추지 말고 원인을 확인·질문한다. 기존 변경·로컬 브랜치를 자동 삭제하지 않는다.

## 구현과 검증

요청 범위 구현과 직접 관련된 테스트·문서를 함께 바꾼다. 수정 중 빠른 관련 검사, 종료 전 변경 영역의 검증을 실행한다. 오류 수정은 재현·회귀 테스트를 남긴다. 사용자 변경을 보존하고 무관한 정리로 범위를 넓히지 않는다.

현재 저장소에서 제공하는 검증 명령은 아래와 같다. 모두 저장소 루트의 Git Bash 기준이며 전체 실행 방법은 [로컬 실행 문서](local-development.md)를 따른다. 테스트 DB를 사용하는 pytest 전에 전용 PostgreSQL/Redis가 준비되어야 한다. 운영 데이터에는 실행하지 않는다.

```bash
# 잠금 파일과 설치 상태
uv sync --locked --check

# Django·migration
uv run --locked --no-sync python apps/backend/manage.py check
uv run --locked --no-sync python apps/backend/manage.py makemigrations --check --dry-run

# Python 정적 검사와 기초 테스트
uv run --locked --no-sync ruff check .
uv run --locked --no-sync ruff format --check .
uv run --locked --no-sync mypy
uv run --locked --no-sync pytest apps/backend/tests
uv run --locked --no-sync pytest packages/map_processing/tests

# Vue: build에 vue-tsc가 포함됨
node scripts/check-node.mjs
npm --prefix apps/web run build
npm --prefix apps/web test

# Compose 구성
docker compose config --quiet
```

- 현재 mypy 범위는 `packages/map_processing/src`다. Django 전체 타입 검사를 통과했다고 표현하지 않는다.
- 현재 pytest/Vitest는 기초 코드 검사다. M0 품질·전체 권한·다층 경로·E2E·운영 복원 검사가 아니다.
- 문서 전용 작업은 변경 문서의 UTF-8·링크·앵커·구조·코드 펜스·충돌 표식과 `git diff --check`를 확인한다. 신규 파일은 diff에 잡히지 않는 부분도 별도로 확인한다. 수동·일회성 검사인지 저장된 스크립트인지 보고한다.
- 공통 verify 스크립트·문서/비밀 검사 자동화·CI는 아직 없다. 이름만 계획된 명령을 실행 가능한 것으로 안내하지 않는다. 기본 문자열 검사는 전문 비밀 탐지·취약점 검사 통과가 아니다.
- 공통 계약·의존성·Docker·workflow 등 공통 기반을 변경하면 영향받는 영역 전체를 검사한다. 필요 도구가 없으면 설치·버전 변경을 임의 진행하거나 검증을 숨기지 않는다.
- 하네스 게이트 구현 시 의도적 실패·누락·취소가 성공으로 처리되지 않는지 검사한다. 최종 MVP는 필수 미구현·미검증 항목을 남긴 채 완료 처리하지 않는다.

| 결과 | 의미 |
| --- | --- |
| `PASS` | 해당 환경에서 실제 검사를 실행해 통과함 |
| `FAIL` | 실행한 검사가 실패함. 기존 실패라고 해도 결과는 실패로 기록하고 근거·영향을 설명함 |
| `NOT_VERIFIED` | 환경·도구 부재 또는 미실행으로 확인하지 못함 |
| `NOT_IMPLEMENTED` | 검사 또는 대상 기능이 아직 구현되지 않음 |

## 승인 범위

- 확인·검토·진단 요청: 읽기와 비변경 진단. 원인을 확인해도 수정 요청 없이 구현하지 않는다.
- 구현 요청: 요청 범위의 코드·테스트·문서, 확정 규칙에 따른 작업 브랜치 생성과 관련 검증.
- 커밋: 완료 보고 후 사용자에게 별도 명시적 승인을 받은 변경만 기록한다.
- push: 승인한 커밋·브랜치만 원격에 올린다. 커밋 승인과 별개다. 기존 커밋 push 요청을 신규 커밋·PR 생성 승인으로 해석하지 않는다.
- PR 생성·최종 검수·병합: 사용자가 직접 진행한다. 에이전트는 초안과 실제 상태만 제공한다. `gh pr create`·자동 PR workflow·자동 병합을 실행하지 않는다.
- 외부 설정·실계정·키 발급·유료 호출·운영 배포·데이터 삭제: 관련 대상과 영향에 대한 별도 승인 범위다. 일반 구현 요청으로 확대 해석하지 않는다.

AI 리뷰는 확정한 별도 설계에 따라 PR 댓글을 작성하는 참고용 자동화다. 사람의 PR 생성·최종 검수·병합을 대체하지 않는다. 향후 신뢰된 리뷰 workflow의 댓글 작성은 PR 자동 생성과 다른 작업이며, 현재는 리뷰 스크립트·키·보호 설정 모두 미구현이다. 자기 PR의 일반 Approve나 양식 체크만으로 최신 SHA 사람 승인 게이트가 구현된 것으로 표시하지 않는다.

## 커밋 메시지

제목은 `유형: 한국어 요약`으로 짧게 작성한다. 유형은 `feature`, `fix`, `refactor`, `chore`, `docs`, `test` 중 하나다. `feat`나 별도 카테고리를 추가하지 않는다.

제목 뒤 빈 줄을 두고 변경 내용과 이유를 한국어로 적는다. 경로·API·식별자는 원래 표기를 유지해도 된다. 검증 결과는 채팅 완료 보고와 PR 본문에 기록하며 커밋 본문에는 넣지 않는다.

```text
docs: 작업 규칙과 수동 PR 작성 양식 정리

변경 내용
- 작업별 문서와 검증 범위를 연결
- 브랜치 흐름과 상세 PR 양식 추가

변경 이유
- 작업 권한과 사람의 검수 단계를 명확히 안내하기 위해
```

기존 커밋의 제목·작성자·이력은 이 규칙 적용을 이유로 자동 수정하지 않는다. 로컬 커밋 작성자는 해당 저장소의 Git 설정을 확인한다. 웹에서 생성되는 병합 커밋의 작성자 이메일은 로컬 설정과 다를 수 있으므로 사용자가 GitHub 이메일 공개 설정도 확인한다. 타인의 이메일·개인 설정을 보고서에 노출하지 않는다.

## PR 초안과 병합 메시지

[상세 PR 양식](../../.github/pull_request_template.md)을 따른다. 제목은 커밋과 같은 유형·한국어 요약을 사용하고, 본문은 관련 작업·번호별 변경 내용·영향 범위·실제 검증·병합 전 확인·리뷰 참고 사항을 자세히 적는다. 해당 없는 항목은 없음으로 적거나 삭제하되 실패·미검증·알려진 제한을 숨기지 않는다.

에이전트는 완료 보고의 사실을 PR 초안에 정리한다. 사용자가 GitHub에서 직접 PR을 생성하고 대상 브랜치·최신 변경·실제 검증을 확인한 뒤 병합한다. 양식 체크박스는 초기 상태를 미체크로 두며 자동 검증 또는 사람 승인 증거를 대신하지 않는다.

병합 메시지가 필요한 경우에도 유형·한국어 요약, 변경 내용·이유를 제공한다. 검증 결과는 PR 본문에 남긴다. 병합 방식과 실행 자체를 에이전트가 임의 선택·수행하지 않는다.

## 채팅 완료 보고

완료 보고는 사용자가 변경과 다음 승인을 판단하는 자료다. 자동으로 커밋이나 PR 댓글에 등록되지 않는다.

1. 변경 내용과 이유, 주요 파일.
2. 작업 브랜치·분기 기준·변경 범위.
3. 실제 실행한 명령·환경·결과와 필요시 직접 확인 시나리오.
4. 알려진 문제·미검증·미구현·의도적으로 하지 않은 범위.
5. 커밋·push 여부와 사용자 수동 PR·검수·병합 등 남은 단계.

로컬 완료, 커밋 완료, 원격 push, PR 생성, 병합, 운영 배포를 각각 구분한다. 규칙 문서 작성만으로 자동 차단·운영 보안·배포가 완료되었다고 보고하지 않는다.
